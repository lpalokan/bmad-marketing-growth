# Mine the Unit from Job Descriptions

<instructions>
Reconstruct the target unit's real jobs-to-be-done, size, shape, and automation
appetite from its own job descriptions — the most reliable confirmed-about-them
source for what the relevant function actually does. Output is a section appended to
the account profile (or `v{n}.md`). Everything here is a **Know** (their own words)
until you fall back to comparable-industry JDs, which are **Assume** — mark
`[confirm]`.
</instructions>

<process>
1. Find the target's own open or recent postings in the relevant function (risk /
   compliance / audit / controls / quality / the function your offering serves). Use
   `WebSearch` / `WebFetch` against the careers site, LinkedIn Jobs, and aggregators.

2. Read the JD **body**, not just the title — it names the unit's real tasks, size and
   shape. Tells: a single maternity-cover or backfill posting = a lean team; a build-out
   with several reqs = investment.

3. Read the **automation appetite** off the tools a JD names (the category you sell,
   plus adjacent: analytics, RPA, Copilot, CCM/continuous monitoring, agentic tooling —
   see the domain overlay for sector-specific tells). A JD asking for the category you
   sell = you are pushing an open door.

4. Read the buyer's **own hiring history** (LinkedIn) — did they build this function
   themselves? If so, respect it: do not pitch cutting the headcount they fought for.
   (This also feeds Cleo's committee map — hand it forward.)

5. Where the target's own postings are thin, use **comparable-industry JDs** for the
   same role as a benchmark only — mark every such inference `[confirm]`, never present
   it as a fact about the target.

6. Write the section: unit tasks, inferred size/shape, automation appetite, hiring
   posture — each JD cited and dated. Note the sharpest **Don't-know** as a meeting
   objective (e.g. "central testing team vs distributed — unclear").
</process>
